## Findings

### 1. High: reclaim silently loses a pending job trimmed off the stream

`internal/queue/queue.go:166` (`Claim`), with `MAXLEN ~ 10000` on `Enqueue`.

When the stream trims an entry that is still in the pending list, the job behind it disappears. Its hash stays RUNNING or QUEUED until the 7-day TTL, it is never dead-lettered, and `submit --wait` on it never gets a report: it runs until its `--timeout` (3 min by default) and exits with an error. Nothing is logged.

On Redis 7, XAUTOCLAIM removes the trimmed entry from the PEL as it reports it, in the reply's third element. go-redis's `XAutoClaimCmd.readReply` discards that element (`rd.DiscardNext()`), so `Claim` never saw it. On Redis 6.2, the entry arrives with no fields, and `Claim` acked it as malformed without a log line. Confirmed with a probe on Redis 7.4: after `XTRIM MAXLEN 0`, the trimmed ID came back only in the third element, and the PEL was empty afterwards. miniredis returns an empty list there, which is why no unit test could have caught this.

Trigger: no workers running for a while, or a crashed worker's entry not yet reclaimed, while the API accepts more than about 10000 submissions.

**Fix:** send XAUTOCLAIM through `Do`, so the trimmed IDs are visible, and log each one at Error. Stop the trim from cutting below the oldest pending ID (for example `XTRIM MINID`), which differs from Appendix B.3.

**Status: logged since `7e3a0b0`; prevention Open, [issue #4](https://github.com/AidanL23/phishcheck/issues/4).**
- **What changed:** `Claim` sends XAUTOCLAIM raw and returns a `ClaimResult` with `Jobs`, `Next`, `Trimmed` and `Malformed`. `reclaimPass` logs each trimmed ID at Error ("pending job lost, its stream entry was trimmed (MAXLEN) before reclaim") and each malformed one at Warn. On Redis 6.2, a trimmed entry is acked and reported as trimmed instead of malformed.
- **Still open:** the job itself can't be recovered, because its job ID went with the entry. Preventing the loss means trimming differently from B.3, which is tracked in [issue #4](https://github.com/AidanL23/phishcheck/issues/4).
- **Tested:**
  - `TestClaimReportsTrimmedPendingEntry` (integration, real Redis): trims a pending entry and expects it in `Trimmed` with an empty PEL. Making `Claim` ignore the third element fails it.
  - `TestClaimAcksAndReportsMalformedEntry` (miniredis) covers the malformed path.
  - The integration test doesn't run in CI yet ([issue #5](https://github.com/AidanL23/phishcheck/issues/5)).

### 2. Low: a reclaimed attempt can hold its entry as long as `ReclaimMinIdle`

`internal/worker/reclaim.go:106`, with the invariant stated at `internal/worker/worker.go:25`.

The comment says `JobTimeout + FinishTimeout` (55 s) must stay below `ReclaimMinIdle` (60 s). That counts only `Handle`'s own time. On the reclaim path, `reclaim` first reads the job hash under a 5 s `FinishTimeout` context. That read happens after XAUTOCLAIM has reset the entry's idle time and before `Handle` starts its clocks. The worst case is 5 + 50 + 5 = 60 s, exactly `ReclaimMinIdle`, so another worker's pass can claim the entry while the first is still writing DONE or acking. The job runs twice, and `attempts` gets an extra bump that can push it to the dead-letter limit early. It needs Redis to be slow enough to hit the timeouts.

**Fix:** count the read in the budget, either by giving it a shorter timeout or by lowering `JobTimeout`. Lowering `JobTimeout` to 45 s would break the guide's 45 s `PHISHCHECK_DEBUG_SLEEP` demo.

**Status: fixed in `7e3a0b0`.**
- **What changed:** the read now has its own `ReclaimReadTimeout` (2 s). A new constant, `MaxHoldTime = ReclaimReadTimeout + JobTimeout + FinishTimeout` (57 s), is the longest a worker holds an entry. The comments in `worker.go` and `reclaim.go` now name it, and the unsafe-idle check in `cmd/worker` uses it.
- **Tested:** `TestMaxHoldTimeBelowMinIdle` fails if `MaxHoldTime` reaches `ReclaimMinIdle`. The slow-Redis interleaving itself isn't reproduced.

### 3. Low: the panic demo steals other workers' jobs

`cmd/worker/main.go:109`

The unsafe-idle guard allowed `PHISHCHECK_RECLAIM_IDLE` as low as 5 s whenever `PHISHCHECK_DEBUG_PANIC=1`, and it only checked its own process. Started next to normal workers, such as the two Compose replicas on Day 6, the panic worker claims their in-flight jobs after 5 s idle, panics on them, and after three reclaim ticks dead-letters real work. The only protection was a WARN line.

**Fix:** refuse to start while `XINFO CONSUMERS` shows other recently active consumers.

**Status: fixed in `7e3a0b0`; startup-only check Open, [issue #6](https://github.com/AidanL23/phishcheck/issues/6).**
- **What changed:** when the reclaim idle is in the unsafe range, `cmd/worker` calls the new `Consumer.OtherActiveConsumers`. It refuses to start if any other consumer talked to Redis in the last `ReclaimMinIdle` (60 s), and the error names those workers. A live worker always shows up within that window, even mid-job, because its reclaim loop runs XAUTOCLAIM every 30 s.
- **Still open:**
  - The check runs once, at startup, so a worker started after the panic worker isn't caught ([issue #6](https://github.com/AidanL23/phishcheck/issues/6)).
  - A worker stopped less than 60 s ago still counts as live, so the §2.5 demo now needs a minute's wait after stopping the others.
- **Tested:**
  - `TestOtherActiveConsumers` (integration, real Redis): a consumer that just read counts as live, and one quiet for longer than the window doesn't. miniredis reports consumer idle as -1 for `XREADGROUP`, so this can't be a unit test.
  - Checked by hand on Redis 7: next to a live worker the panic demo exits 1 and names it; on a fresh group it starts.
  - The integration test doesn't run in CI yet ([issue #5](https://github.com/AidanL23/phishcheck/issues/5)).

### 4. Low: the dead-letter stream cap is 10x the spec

`internal/queue/queue.go:190`

`DeadLetter` reused the main stream's `maxLen` (10000). Appendix B.3 specifies `MAXLEN ~ 1000` for `phishcheck:jobs:dead`. A poison sample submitted in a loop would fill the dead-letter stream to about 10000 entries, 10x what B.3 budgets for. The entries also carry `stream_id`, `attempts` and `dead_lettered_by`, which B.3 didn't list.

**Fix:** a separate `deadMaxLen = 1000`. Update B.3 for the extra fields.

**Status: fixed.** `7e3a0b0` adds `deadMaxLen = 1000` and uses it in `DeadLetter`. The extra fields stay, and B.3 in the local build guide now lists them. Not tested: miniredis doesn't model approximate trimming, and the change is one constant.

### 5. Low: an ordinary failure on attempt 3 was dead-lettered

`internal/worker/reclaim.go:127`

`reclaim` ran the attempts check before the FAILED check. That order was needed so a `giveUp` whose dead-letter step had failed would be retried. But FAILED with `attempts` 3 looked the same whether `giveUp` or `fail()` wrote it. So an ordinary error on the third attempt, whose XACK was then lost, got a dead-letter record. The same thing on attempts 1 or 2 was just acked. An analyst triaging the dead-letter stream would see a false poison job.

**Fix suggested in the review:** a marker field written by `giveUp`.

**Status: fixed in `7e3a0b0`, without a marker.**
- **What changed:** `giveUp` now writes FAILED, the dead-letter record and the XACK in one MULTI/EXEC. The new `store.SetJobStateIn` adds the FAILED write to the queue's transaction through a new `also` argument on `Consumer.DeadLetter`. Since `giveUp` can no longer leave a FAILED entry pending, a pending FAILED entry always means "`fail()` recorded it, then the XACK was lost". `reclaim` now checks DONE, then FAILED, then attempts, and acks FAILED on any attempt.
- **Tested:** in `TestReclaimCases`, "FAILED at max attempts is acked, not dead-lettered" expects an ack and no dead-letter entry. "RUNNING at max attempts is dead-lettered" expects FAILED, one dead-letter entry and an empty PEL. `TestDeadLetterRecordsAndAcks` checks that the `also` commands commit.
- **Mutation checks:** each of these fails `TestReclaimCases`: moving the attempts check back above FAILED, moving it above DONE, and dropping the FAILED write from `giveUp`.

### 6. Nit: the code and §2.7 disagree on cancelling a blocking read

`cmd/worker/main.go:157` (the `stepStop` comment)

Guide §2.7 says go-redis cancels a blocking `XREADGROUP` when the context is cancelled. The comment says a read already blocking waits out the 5 s BLOCK. At review time this was unverified.

**Fix:** time a cancel during `Next`, then correct whichever text is wrong.

**Status: no code change needed; guide corrected.**
- **Which text is wrong:** the comment is right. On both miniredis and Redis 7.4, `Next` returned after the full 5 s BLOCK with `ErrNoJob`, even though the context was cancelled at 200 ms. The worker still shuts down correctly, but SIGTERM can take up to 5 s longer than the in-flight job.
- **Guide:** §2.7 in the local build guide now says this. The guide isn't in the repo.
- **Tested:** `TestNextIgnoresCancelUntilBlockEnds` (added in `7e3a0b0`) locks the behavior in. It's skipped with `-short`.

### 7. Low: the §2.6 timeline formatting had no unit test

`cmd/phishcheck/main.go:364` (`timeline.update`)

`TestWaitForReport` only fed statuses with nil timestamps, so every line printed `-`. These had no unit test:
- the `0.0s`, `+N.Nms` and `+N.Ns` branches of `timeline.line`
- the extra RUNNING line when `attempts` changes
- rebuilding missed phases when the first status is already DONE

The reclaim line in particular was only checked by the manual demo, because e2e has no reclaim. The review also listed the worker's timeout path as untested, since `JobTimeout` was a fixed constant.

**Fix:** table cases with fixed timestamps, plus an injectable job timeout for the worker.

**Status: fixed in `7e3a0b0`.**
- **`TestTimeline`** covers five cases: every phase in ms, first status already DONE (s offsets), a reclaim with a second RUNNING line, dead-letter after three attempts, and negative clock skew.
- **`TestHandleTimeoutFailsAndAcks`** covers the timeout path. It shortens the timeout through a new unexported `jobTimeout` field that only tests change, and expects FAILED with "timed out after 100ms" and an ack.

## Checked, OK

**1. Error handling.**
- `Handle`'s switch gives each outcome its own branch: success, panic, timeout, failed Redis write, and ordinary error. Panic is checked before timeout, and timeout before a failed write.
- A failed `StartAttempt`, `PutReport` or DONE write is tagged `errWrite` with two `%w`, so `errors.Is` matches both `errWrite` and the Redis error. These entries are left pending, not acked.
- If the FAILED write in `fail()` fails, the entry isn't acked either.
- `reclaim` separates a missing job hash (`store.ErrNotFound`, dead-lettered) from a Redis read error (left pending).
- Malformed stream entries are acked and logged, apart from Redis errors, in both `Next` and `Claim`.
- `config.boolean` rejects `yes` or `on` instead of reading them as false, and `nonNegativeDuration` rejects negative values.

**2. `clean()`.**
- Day 2's new terminal output is the `--wait` timeline. It prints a state enum, offsets computed from server timestamps, the worker ID (server-computed, so raw by design) and `attempt N`.
- The job's error string travels in `JobStatus` during a panic retry, but the timeline doesn't print it.
- The worker error shown when `--wait` ends in FAILED still goes through `clean()`, covered by `TestWaitForReport`'s "failed: worker error is cleaned".
- No email-derived text was added to Redis key names: keys use only the job ID and the stream ID.

**3. Resource cleanup.**
- `StartAttempt` and every `SetJobState` refresh the job hash's TTL inside the same MULTI/EXEC (`TestJobLifecycle`).
- `RunReclaim`'s ticker and `debugSleep`'s timer are stopped with `defer`.
- Every `WithTimeout` in `Handle` and `reclaim` is cancelled on all paths.
- Both streams now have a length cap (#4).
- Every entry is acked, dead-lettered, or deliberately left pending for reclaim. e2e checks "nothing left pending" after each scenario.
- On shutdown, `run` waits for the reclaim goroutine before returning, so the deferred `rdb.Close` can't run under a live job. e2e checks the "worker stopped" line and exit 0.

**4. Concurrency.**
- The worker has exactly two goroutines that can be mid-job: the main loop, which runs jobs inline, and the reclaim loop, which `run` waits for with `reclaimWG.Wait`.
- `Worker` holds no mutable state after `New`.
- A job that was read always runs on `context.WithoutCancel`, so SIGTERM never aborts its Redis writes partway.
- `claimCount` is 1, so a claimed entry runs right away instead of idling in a batch.
- `StartAttempt` bumps `attempts` and sets RUNNING in one MULTI/EXEC. DONE is still written after the report.
- `go test -race ./...` is clean locally.
- The timing budget (#2) and the panic-demo guard (#3) are the exceptions.

**5. Comments.**
- **Wrong, and fixed:** the JobTimeout/MinIdle invariant comment (#2).
- **Confirmed by test:** the `stepStop` comment (#6).
- **Checked and accurate:**
  - "Acking an entry that is no longer pending is a no-op"
  - "Inside a pipeline, `Val()` is only valid after EXEC has returned"
  - "Redis doesn't roll back, but EXPIRE can't fail on a key HSET just wrote"
  - "A time.Ticker drops ticks while the receiver is busy"
  - `RunReclaim` scanning once right away before the first tick
  - "HGETALL returns an empty map, not redis.Nil"
  - `EnsureGroup` starting at "0" so jobs enqueued before the first worker are delivered (`TestEnsureGroupIsIdempotentAndKeepsEarlierJobs`)
