## Findings

### 1. Medium: the worker drops a job read just before shutdown

`cmd/worker/main.go:101-115`

```go
msg, err := q.Next(ctx)
switch {
case errors.Is(err, queue.ErrNoJob): continue
case ctx.Err() != nil:            continue   // <- also true when err == nil
...
```

Suppose `XREADGROUP` returns an entry and then SIGTERM lands before the `switch` runs. The second case matches even though `err == nil` and `msg` holds a real job. The loop exits without calling `handle`. The entry sits in the group's pending list, owned by a consumer that no longer exists. Nothing re-reads it (`>` only delivers new entries, and there is no reclaim until Day 2), and the job hash stays QUEUED until its TTL expires. Meanwhile `submit --wait` waits until its own timeout.

The window is small, but the job is lost silently, and `docker stop` during a burst is exactly when it opens.

**Fix:** only treat cancellation as the cause when there *is* an error: `case err != nil && ctx.Err() != nil:`. Or, once Next has returned a job, always `handle` it (see #2).

**Status: fixed.** The loop's decision is now a pure function, `nextStep(err, stopping)`, which returns `stepHandle` whenever `err == nil`, whether or not shutdown has started. `TestNextStep` covers that case, and it fails against the old case order.

### 2. Medium: shutdown mid-job aborts the job's writes; the comment says it can't

`cmd/worker/main.go:95-96`: "Check for shutdown between jobs, never in the middle of one."

The loop only *checks* between jobs, but the signal context is also passed into `handle`, then `process`, and from there into every `SetJobState`, `GetEmail`, `PutReport` and `Ack`. A SIGTERM mid-job cancels whichever Redis call is in flight. Then:

- `process` fails with `context canceled`, and `handle` tries to record FAILED **with the same cancelled ctx** (line 138), which fails too.
- `Ack` (line 148) uses the same ctx and fails, so the entry stays pending.
- Result: the job hash says RUNNING forever (until the TTL), the entry stays unacked, and the log shows three errors for what was a normal shutdown.

The comment at line 46 ("Letting the in-flight job finish before exiting is §2.7") flags graceful drain as future work, but the comment at line 95 tells a reader it already behaves that way.

**Fix (small, and it covers #1):** give the job its own context that ignores the shutdown signal but still has a bound:

```go
jobCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 30*time.Second)
handle(jobCtx, logger, st, q, workerID, msg)
cancel()
```

Docker's 10 s SIGKILL still bounds the worst case. If you'd rather keep this for §2.7, change the line-95 comment to say a job in progress *is* interrupted.

**Status: fixed.** `run` passes `context.WithoutCancel(ctx)` to `handle`. Inside `handle`, `process` runs under a 30 s `jobTimeout`, and the FAILED write and XACK get their own 5 s `finishTimeout`, so even a job that timed out is recorded and acked. The comments at the top of `run`, on the loop, and on `handle` now describe this. Not tested directly: interrupting a millisecond stub job mid-flight can't be done deterministically. The e2e shutdown checks (exit 0, "worker stopping") still pass.

### 3. Medium: file paths reach the terminal without `clean()`

`cmd/phishcheck/main.go:540` (also 535, and `main` at 64 for `submit`)

`submit-dir` cleans `results[i].file`, but then prints `err`, and every `submitFile` error embeds the full path: `"%s is empty"`, `"%s is a directory"`, `"read %s: …"`, and `*os.PathError`. The file name is attacker-influenced: mail clients name a saved `.eml` after its Subject, and `samples/real/` holds exactly those files.

Reproduced with an empty file named `ESC[31mINVOICE ESC[0m CR .eml`:

```
\x1b[31mINVOICE\x1b[0m\r.eml -> ERROR: /…/evil/^[[31mINVOICE^[[0m^M.eml is empty
```

The cleaned name on the left is followed by the raw ESC and CR on the right. A CR plus a forged line can overwrite what the analyst sees.

**Fix:** clean the whole error text where it is printed: `clean(err.Error(), 0)` at 540 and 535, and in `main`'s final `Fprintln`. (`clean` escapes `\n` too; none of the CLI's errors are multi-line.) Adding one more `TestSubmitFileErrors` case locks this in.

**Status: fixed.** `main`'s final error line, the `submit-dir` per-file ERROR line and the wait errors after the table now all print `clean(err.Error(), 0)`. The "stopped at" error is cleaned when `main` prints it. `TestSubmitDirCleansErrors` (fails on the old code) and two new e2e checks, using a real file with ESC and CR in its name for both `submit` and `submit-dir`, lock it in.

### 4. Low: `submitFile` returns mid-stream without ending the RPC

`cmd/phishcheck/main.go:234, 243`

On a non-EOF `Send` error or a file read error, `submitFile` returns without `CloseAndRecv` and without cancelling the stream's context. gRPC keeps the stream open until the context ends. In `submit-dir`, that context is the whole command's (5 min default), so the stream stays open while the remaining files upload. On the other end, the server sits in `Recv` holding the partial upload in memory (up to the cap).

**Fix:** put `ctx, cancel := context.WithCancel(ctx); defer cancel()` at the top of `submitFile`.

**Status: fixed.** `submitFile` now opens the stream on its own `context.WithCancel` and defers the cancel, so every return path ends the stream. `TestSubmitFileEndsStreamOnEarlyReturn` covers this and fails without the change.

### 5. Low: no bound on the filename or on how long an upload may take

`internal/api/server.go:61`

- `filename` comes from the client, isn't counted toward `maxBytes`, and has no length cap. One message can carry ~4 MB of name (gRPC's default per-message limit). That name gets stored in the job hash, copied into the report, and written to the logs.
- Nothing bounds how long a `SubmitEmail` stream may stay open. A client that sends 25 MB − 1 and never closes holds that buffer forever, and N such clients hold N × 25 MB.

That's acceptable for today's local, unauthenticated server, but write it down before Day 6.

**Fix:** reject a filename over 255 bytes with InvalidArgument. Add a server-side deadline on uploads, or `grpc.MaxConcurrentStreams` plus keepalive enforcement.

**Status: fixed.** A filename over 255 bytes is rejected with InvalidArgument; the log line records only its length. The receive loop moved into `receive`, which runs in its own goroutine, and `SubmitEmail` waits for it for at most `uploadTimeout` (2 minutes) before returning DeadlineExceeded. Returning ends the RPC, which unblocks the goroutine's `Recv`. Covered by two new `TestSubmitEmailRejections` cases (256 bytes rejected, exactly 255 accepted) and `TestSubmitEmailUploadTimeout`, which also checks the goroutine exits. Still not done: there's no limit on concurrent connections. Worth adding before Day 6.

### 6. Low: client cancellation in `SubmitEmail` is reported as a server failure

**Status: fixed.** A new `canceledStatus(ctx)` helper runs before each Internal in `SubmitEmail`, `lookupJob` and `GetReport`. `TestSubmitEmailClientCanceled` checks for Canceled and that no ERROR line is logged, and it fails without the helper.

### 7. Low: a malformed stream entry takes the Redis-error branch

`cmd/worker/main.go:112` (since the fix for #1, `nextStep` returns `stepBackoff` for it; `TestNextStep` records that behavior)

`Next` acks a malformed entry and returns `ErrMalformedEntry`. The worker treats that like a dead connection: it logs at ERROR as `"read from stream"` and sleeps 1 s. The e2e run shows the log line: `"msg":"read from stream","error":"queue: malformed entry has no job_id: entry …"`.

### 8. Low: `lookupJob` accepts more than canonical UUIDs

`internal/api/server.go:134-137`: "Rejecting anything else up front means junk input never becomes part of a Redis key name."

`uuid.Parse` also accepts `{…}`, `urn:uuid:…`, 32 hex characters without dashes, and uppercase (all verified). Each of those becomes a different Redis key from the stored lowercase one. The practical bug: paste a real job ID in uppercase and you get "not found or expired".

**Fix:** normalize, `u, err := uuid.Parse(id); …; id = u.String()`, so every form finds the job. Or require `u.String() == id`.

**Status: fixed.** `normalizeJobID` parses the ID and returns `u.String()`, so every accepted form finds the job, and only the canonical form becomes a key name. `TestNormalizeJobID` covers all five forms. In e2e, `report` with an uppercase copy of a real ID succeeds and returns the lowercase ID.

### 9. Low: JSON outputs aren't terminal-safe for bidi or C1 characters

`cmd/phishcheck/main.go:459`, and the API's slog lines that log `filename`.

protojson and slog's JSON handler both escape C0 controls, so ESC, CR and LF are safe; that part is tested. But both pass U+202E (right-to-left override), C1 controls such as U+009B (8-bit CSI) and zero-width characters through raw. Verified: `{"filename":"a\u202eb\u009bc"}` comes out with the literal characters. So `phishcheck report ID --json` printed straight to a terminal, or `docker compose logs api`, can still reorder text.

Raw output is intended for `--json` (the comment at 459 says so). The risk is someone assuming JSON output is safe to read in a terminal.

**Fix:** none needed now. If you want, add one line to the `printJSON` comment: "pipe it to jq; raw output is not terminal-safe".

**Status: fixed (comments).** The `--json` comment in `runReport` and the filename comment in `receive` now say outright that JSON escaping doesn't make the output terminal-safe. The behavior is unchanged on purpose.

## Checked, OK

**1. Error handling.** Worker errors are wrapped with the step that failed (`set RUNNING`, `get email`, `put report`). The store separates `ErrNotFound` from Redis errors using `errors.Is(redis.Nil)` and the empty-map case of `HGETALL`. gRPC handlers return fixed messages and send the detail to the log. `rpcErr` keeps `errUnreachable` reachable through `errors.Is`, which `submit-dir` depends on. `config.Load` reports every bad variable at once (now tested). `submitFile` handles `n > 0` before `io.EOF` and gets the real status from `CloseAndRecv` after `Send` returns `io.EOF` (both tested). `report` exits non-zero with nothing on stdout for non-DONE states.

**2. `clean()`.** Covered: `printReport` (filename, rule_id, evidence), worker error strings in `waitForReport` and `runReport`, the success line in `submit`, file names in the `submit-dir` table and job mapping. `clean()` itself is checked against every code point (`TestCleanEveryRuneIsSafe`) and fuzzed: it never emits a non-graphic rune, and it leaves safe input unchanged. Printed raw on purpose: sha256, job ID and worker ID, which the server computes. Untrusted text is never used as a path or key: the filename is only stored and logged, and job IDs are UUID-checked before they become key names (but see #8).

**3. Resource cleanup.** All three keys get a TTL, verified live in e2e (`TTL` is 3599 for email, job and report). The stream is capped (`MAXLEN ~ 10000`). An over-cap upload stores nothing (e2e: job count unchanged). Every read entry gets XACKed, including malformed ones (e2e: `XPENDING` is 0). The WatchReport ticker is stopped. The `sleepCtx` timer is stopped. CLI connections and files are closed with `defer`. The API stops gRPC (graceful first, then forced after 5 s) and only then closes Redis. In e2e, both services exit 0 on SIGTERM.

**4. Concurrency.** `submit-dir --wait`: each goroutine writes only `results[i]`, `wg.Wait` happens before the table is read, at most 16 streams are open at once, and each loop iteration gets its own `i`. That path runs under `-race` in CI. `Server` holds no mutable state. Write order makes work visible last: email, then job hash, then XADD in the API; report, then DONE in the worker. The consumer group gives each entry to one worker. The shutdown path is the exception (#1, #2).

**5. Comments.** Checked and accurate: the chunk math ("400 allocations" at 25 MB), "Read can return the last bytes and io.EOF", "Send only returns io.EOF", "HGETALL returns an empty map, not redis.Nil", "Acking an entry that is no longer pending is a no-op", "Serve only returns nil after Stop/GracefulStop", the Docker 10 s SIGKILL, the "report key expired just before the job hash" window in `GetReport` (the job hash's TTL is refreshed after the report is written, so this window really exists), `emlFiles` skipping symlinks (tested), and "EmitUnpopulated" making `score` 0 rather than missing (tested).
